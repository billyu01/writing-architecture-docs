# 07 · 如何验证「用本技能产出的架构文档」合格

> 目的：让「skill 是否真的能产出合格文档」可复现，而不是靠作者自述。
> 三级验证：结构（机器）→ 内容（人判断）→ 图（机器+人眼）。三级都过才算合格。

## 1. 结构验证（机器）

在文档目录执行：

```bash
python3 <skill>/scripts/check_architecture_docs.py <文档目录> --html <可视版.html>
```

通过标准：
- `0 error`；
- warning 逐条判断，不能直接忽略；
- 必须覆盖：4+1 五视图、DDD 领域建模要素、状态机/Outbox/账本图、文档信息与架构摘要、关键机制设计卡、需求追溯、核心接口、测试验收、无裸代号、构建命令不入正文、部署口径一致。

常见失败信号：
- `4+1 视图` 缺进程/开发/场景；
- `领域建模` 缺聚合/值对象/领域事件/仓储/工厂；
- `图种覆盖` 缺状态机/Outbox/账本；
- `一致性` 出现「事务外 outbox」「两个聚合与同事务并存」；
- `评审项` 手机号只有 hash、充值缺账户、缺 RBAC/索引/容量。

## 2. 内容验证（人判断）

逐项回答「是/否 + 证据」：

- [ ] 每个核心机制都有「设计方案 / 理由 / 异常场景 / 验证方式」四格（设计卡）。
- [ ] 每条需求能追到设计落点与验收方式（追溯表）。
- [ ] 每个验收点有可执行判据与失败路径，不是口号。
- [ ] 事务边界写清了条件更新、重试、超时、热点。
- [ ] 幂等分永久业务约束与请求幂等，不靠 TTL 保证账务。
- [ ] 充值/积分账户归属有业务定义（会员级/门店级、门店额度/会员储值）。
- [ ] 会员合并有别名映射与余额合并规则。
- [ ] 导入有重复范围、部分成功、断点续跑、批次大小。
- [ ] 权限有 RBAC 矩阵，门店范围来自服务端上下文。
- [ ] 有容量模型与 SLO，指标有测量方法和失败表现。

## 3. 图验证（机器+人眼）

```bash
python3 <diagram-skill>/scripts/check_architecture_diagrams.py <文档.html 或 assets>
python3 <diagram-design>/scripts/self_check.py <每张图.html>
```

通过标准：
- `0 error`，warning 逐条判断；
- 每张图「一张图只回答一个问题」；
- 部署图不出现 infra 适配器/仓储/领域服务作为独立部署节点；
- 限界上下文图不混系统调用/消息总线，并有图例；
- 时序图有事务边界与异常/重试分支；
- 状态 ≥4 的对象有状态机图；outbox 有事件流转图；账本有对账图；
- 每张图有编号、图注、源文件、索引行，且能内联进 HTML。

## 4. 可复现的验证样例

- **正例**：一份按本技能产出的完整架构文档（含 13 张图）应通过文档检查与配图检查，结果为 0 error / 0 warning。
- **反例**：故意写坏的文档应被检查器拦下（缺章节、裸代号、事务外 outbox、手机号只有 hash、缺设计卡等）。
- **安装一致性**：仓库 `skills/` 与 `~/.agents/skills/` 逐文件 diff 为空。

## 5. 何时算「合格」

三级全部通过，且：
- 文档能独立回答「系统由什么组成、数据在哪、请求怎么走、部署几个单元、失败怎么办」；
- 研发能按模块分册实现，测试能按验收点写用例，运维能按部署/故障章节操作；
- 未决项有默认走法与负责人/生效时点。

只要有一级不过，就不算「用技能产出了合格文档」；先修 skill 或修文档，再复验。

# DDD 方法论（战略 + 战术）

> 用途：从业务边界到聚合设计，完整落地 DDD；每条都给出步骤、产物、检查清单、误用。

## 1. 定义与适用

DDD（Domain-Driven Design）用限界上下文划分模型边界，用统一语言对齐业务与代码，用聚合保证一致性。适用于业务复杂、规则多、需要长期演进的系统；不适用于简单 CRUD 工具。

## 2. 战略设计

### 2.1 子域与限界上下文
- **子域**：业务领域的划分（核心域/支撑域/通用域）。核心域是竞争差异，投入最多；通用域优先买/复用。
- **限界上下文**：模型生效的边界；一个上下文内的术语、模型、团队保持一致。
- **步骤**：
  1. 用事件风暴/领域故事梳理业务事件与命令；
  2. 按语言变化、团队边界、事务边界聚类成上下文；
  3. 标核心/支撑/通用，决定投入；
  4. 给每个上下文写一句话职责与「不做什么」。
- **产物**：上下文清单、上下文映射图、上下文职责表。

### 2.2 统一语言
- 术语表：中文名、英文标识、定义、弃用叫法。
- 规则：代码、文档、图、API 用同一套词；改名全仓同步。

### 2.3 上下文映射（7 种关系）
| 模式 | 含义 | 使用条件 |
|---|---|---|
| 共享内核 Shared Kernel | 双方共同维护一小部分模型 | 团队紧密协作、模型稳定 |
| 客户-供应商 Customer/Supplier | 下游依赖上游，上游承诺接口 | 上下游团队可协调 |
| 遵奉者 Conformist | 下游直接沿用上游模型 | 上游强势、下游无谈判力 |
| 防腐层 ACL | 下游加转换层隔离上游模型 | 外部/遗留模型会污染本域 |
| 开放主机服务 OHS | 上游提供稳定公开协议 | 多下游复用 |
| 发布语言 Published Language | 用公开契约（事件/ schema）交换 | 跨上下文异步集成 |
| 分离方式 Separate Ways | 不集成，各自实现 | 集成成本高于收益 |

- **步骤**：为每对上下文选模式，标方向（上游/下游）、保护方（谁做 ACL）、契约（API/事件）。
- **检查**：每条关系有方向、模式、契约；共享内核不是独立服务/消息总线。

## 3. 战术设计

### 3.1 聚合与聚合根
- **定义**：聚合是一致性边界；外部只能通过聚合根访问；一个事务只修改一个聚合（或明确声明的例外）。
- **设计规则**：
  1. 聚合尽量小，只包含必须同事务一致的实体/值对象；
  2. 聚合根有全局唯一标识；
  3. 聚合内实体只被根引用；
  4. 跨聚合用 ID 引用，不用对象引用；
  5. 跨聚合强一致用单事务（需声明）或 saga 补偿；
  6. 聚合不直接依赖仓储实现，仓储接口属于领域层。
- **产物**：聚合表（根/内部实体/值对象/不变量/一致性边界）。

### 3.2 实体与值对象
- 实体：有唯一标识与生命周期（会员、券）。
- 值对象：无标识、不可变、按值相等（金额、手机号哈希、积分值）。
- 检查：值对象不可变；实体的相等基于 ID；金额/积分用整数并先判类型。

### 3.3 领域事件
- 命名用过去式（CouponRedeemed）；携带发生事实所需的最小信息；落库（outbox）与业务同事务；订阅方幂等。
- 事件表：事件、触发条件、携带信息、订阅方、是否落库。

### 3.4 领域服务
- 当逻辑跨多个实体/聚合、不属于单个实体时使用；无状态；编排而非持有数据。
- 例：核销服务、对账服务、发券服务。

### 3.5 仓储与工厂
- 仓储：每个聚合根一个仓储接口；只暴露聚合级操作；不暴露 SQL/查询构造器。
- 工厂：复杂聚合的创建/重建；保证创建即合法（不变量）。

### 3.6 不变量与生命周期
- 不变量：必须始终为真的规则（余额=流水合计、券核销幂等）。
- 生命周期：状态集合、合法迁移、守卫条件、非法迁移行为；状态 ≥4 的对象补状态机图。

## 4. 落地步骤（从业务到代码）

1. 事件风暴：列业务事件、命令、角色、聚合候选。
2. 划上下文：按语言/团队/事务边界聚类；画上下文映射。
3. 选聚合：每个上下文找一致性边界；写聚合表。
4. 定事件：每个聚合产出哪些事件；是否跨上下文。
5. 定仓储/工厂/服务：接口归属领域层。
6. 写不变量与状态机：每条可测。
7. 映射到数据模型：ER 只作持久化视图，不反过来主导领域模型。
8. 用场景验证：每个用例只改必要聚合；跨聚合有一致性方案。

## 5. 检查清单

- [ ] 有上下文清单、职责、不做什么。
- [ ] 上下文映射每条有方向/模式/契约/保护方。
- [ ] 每个聚合有根、内部实体/值对象、不变量、一致性边界。
- [ ] 跨聚合引用只用 ID；跨聚合一致性有明确方案。
- [ ] 领域事件有命名、触发、载荷、订阅方、落库策略。
- [ ] 仓储接口属于领域层；每个聚合根一个仓储。
- [ ] 状态机有守卫与非法迁移处理。
- [ ] ER 只是数据模型子节，没有替代领域建模。

## 6. 常见误用

| 误用 | 后果 | 修正 |
|---|---|---|
| 把 ER 当领域模型 | 只有表没有业务规则 | 补聚合、事件、不变量、领域服务 |
| 聚合过大 | 事务冲突、性能差 | 拆小聚合，跨聚合用事件/补偿 |
| 跨聚合单事务不声明 | 与 DDD 边界矛盾 | 声明例外理由，或改 saga |
| 领域事件当同步调用 | 耦合上下文 | 用 outbox/发布语言异步 |
| 贫血模型 | 业务规则散落 service | 把规则放进聚合/值对象 |
| 共享数据库 | 上下文边界被穿透 | 每上下文自有数据，跨上下文走接口 |

## 7. 与其他理论关系

- 与 4+1：限界上下文/聚合支撑逻辑视图；领域事件支撑进程/运行时视图。
- 与 C4：上下文映射对应 Context 图；聚合对应 Component/Code。
- 与一致性理论：聚合边界决定事务边界；跨聚合用 outbox/saga（见 04）。
- 与数据架构：仓储对应数据访问；ER 对应持久化模型。

# 架构决策：ADR / MADR / 决策质量 / 评审

> 用途：把「为什么这样选」变成可追溯、可推翻、可评审的决策记录，而不是散落在聊天记录里。

## 1. ADR（Architecture Decision Record）

### 1.1 定义
ADR 记录一个重要架构决策的背景、决策、状态与后果，供后续维护者理解决策理由与边界。

### 1.2 结构
| 字段 | 要写什么 |
|---|---|
| 编号/标题 | 唯一、可引用 |
| 状态 | 提议/已接受/已取代/已废弃 |
| 背景 | 问题、约束、驱动因素 |
| 备选 | 至少 2 个可行方案 |
| 决策 | 选哪个、为什么 |
| 后果 | 正面/负面/代价/风险 |
| 推翻条件 | 什么情况下重新评估 |
| 关联 | 需求、模块、其他决策 |

### 1.3 使用步骤
1. 识别需要决策的点（技术选型、边界、一致性、部署形态）。
2. 每个决策写至少两个备选，列代价。
3. 记录决策与理由，标可逆性。
4. 决策变化时新增 ADR 并标「取代」关系，不篡改历史。
5. 在架构正文引用 ADR 编号。

### 1.4 检查清单
- [ ] 每个关键决策有 ADR。
- [ ] 有备选与代价。
- [ ] 有推翻条件。
- [ ] 有状态与取代关系。
- [ ] 正文可追溯到 ADR。

### 1.5 常见误用
- 只写结论；
- 没有备选；
- 决策不可逆却不标；
- 改了决策不记录。

---

## 2. MADR（Markdown ADR）

### 2.1 定义
MADR 是 ADR 的轻量 Markdown 模板，增加「决策驱动因素」「考虑的选项」「利弊」等字段，适合仓库内维护。

### 2.2 模板字段
- 标题、状态、背景与问题；
- 决策驱动因素；
- 考虑的选项（每个列优缺点）；
- 决策结果；
- 后果（正面/负面/风险）；
- 确认方式（如何验证决策有效）。

### 2.3 使用步骤
1. 用 MADR 模板建文件，放 `docs/adr/`。
2. 每个决策一个文件，编号递增。
3. 在架构总览汇总表引用。
4. 定期复审过期决策。

### 2.4 检查清单
- [ ] 有驱动因素。
- [ ] 每个选项有优缺点。
- [ ] 有确认方式。
- [ ] 有复审机制。

## 3. 决策质量评估

### 3.1 评估维度
| 维度 | 问题 |
|---|---|
| 问题定义 | 解决的是真问题吗？ |
| 备选完整性 | 是否只考虑了一个方案？ |
| 证据 | 依据是实测/数据/权威资料，还是感觉？ |
| 权衡 | 代价与收益是否写清？ |
| 可逆性 | 错了能否回退？ |
| 可验证 | 怎么知道决策有效？ |
| 一致性 | 与其他决策/约束冲突吗？ |

### 3.2 使用步骤
1. 每个关键决策按七维打分/检查。
2. 低分项补证据或降级为「待验证」。
3. 冲突决策提交评审。
4. 决策生效后跟踪验证指标。

### 3.3 检查清单
- [ ] 七维都过。
- [ ] 无证据的结论已标「未核」。
- [ ] 冲突已解决。
- [ ] 有生效后验证。

---

## 4. ATAM 权衡分析（决策层）

### 4.1 使用步骤
1. 把决策与质量属性场景关联。
2. 标敏感点（哪个参数影响哪个质量）。
3. 标权衡点（一个参数影响多个质量）。
4. 写风险与非风险。
5. 给出改进建议与优先级。

### 4.2 检查清单
- [ ] 决策关联质量场景。
- [ ] 敏感点/权衡点已标。
- [ ] 风险有缓解。
- [ ] 有优先级。

---

## 5. 架构评审流程

### 5.1 角色
- 架构师：讲设计、回应问题；
- 评审人：业务/开发/测试/运维/安全；
- 记录人：记录问题与结论；
- 决策人：拍板与资源。

### 5.2 步骤
1. 评审前发材料与检查清单。
2. 评审会：按视图讲，逐条对质量场景。
3. 记录问题分级（P0/P1/P2）与负责人。
4. 修复后复审，逐条关闭。
5. 评审结论写入报告与修订史。

### 5.3 检查清单
- [ ] 材料提前发。
- [ ] 按视图与场景评审。
- [ ] 问题有分级/负责人/时点。
- [ ] 复审关闭。
- [ ] 结论入档。

### 5.4 常见误用
- 评审变宣讲；
- 问题不记录；
- 不复审；
- 评审结论不落到文档。

---

## 6. 与其他理论关系
- ADR 是决策的载体；ATAM 提供权衡分析；质量场景提供评估输入；IEEE 42010 提供视图与关注点框架。
- 决策记录反向约束逻辑/进程/部署设计，形成「决策→设计→验证」闭环。

# 一致性与消息：ACID / CAP / PACELC / 幂等 / Outbox / Saga

> 用途：把「数据不能错」落到事务边界、隔离级别、幂等、异步投递与补偿的完整方法。

## 1. ACID 与隔离级别

### 1.1 定义
事务的原子性（全成或全败）、一致性（约束保持）、隔离性（并发互不干扰）、持久性（提交不丢）。

### 1.2 隔离级别与异常
| 级别 | 避免 | 仍可能 |
|---|---|---|
| 读未提交 | 脏写 | 脏读、不可重复读、幻读 |
| 读已提交 | 脏读 | 不可重复读、幻读 |
| 可重复读 | 脏读、不可重复读 | 幻读（视实现） |
| 串行化 | 全部 | 性能下降、冲突重试 |

### 1.3 使用步骤
1. 列出每个写用例的「必须同生共死」的写操作。
2. 划事务边界：一个事务只改一个聚合（DDD）或明确声明例外。
3. 选隔离级别：默认读已提交；涉及余额/库存用条件更新或可重复读/串行化。
4. 写冲突处理：重试次数、退避、超时、最终失败返回。
5. 写失败路径：回滚后状态、幂等重试、补偿。

### 1.4 检查清单
- [ ] 每个写用例有事务边界说明。
- [ ] 跨聚合/跨服务没有默认单事务。
- [ ] 隔离级别与业务异常匹配。
- [ ] 有冲突重试与超时策略。
- [ ] 有回滚后的状态与补偿说明。

### 1.5 常见误用
- 「用了事务」但没写边界；
- 先读余额再写回（非原子）；
- 跨服务用本地事务；
- 重试不幂等。

## 2. CAP 与 PACELC

### 2.1 定义
CAP：网络分区（P）发生时，只能在一致性（C）与可用性（A）之间取舍。PACELC：无分区（E）时，还要在延迟（L）与一致性（C）之间取舍。

### 2.2 使用步骤
1. 标出系统里哪些数据/操作是「分区敏感」的。
2. 为每类数据选 CP 或 AP，并写理由。
3. 写分区期间的降级行为（拒绝写、只读、排队、冲突合并）。
4. 写恢复后的冲突解决（版本号、最后写入胜、业务合并）。
5. 用 PACELC 检查正常时的延迟/一致性取舍。

### 2.3 检查清单
- [ ] 关键数据标了 CP/AP。
- [ ] 分区期间行为明确。
- [ ] 恢复后的冲突解决明确。
- [ ] 没有「既要强一致又要低延迟」的空话。

### 2.4 常见误用
- 把 CAP 当三选二口号；
- 不写分区行为；
- 最终一致却按强一致设计前端。

## 3. 幂等（业务幂等 vs 请求幂等）

### 3.1 定义
同一业务操作重复执行，结果与执行一次相同。分两层：
- **业务唯一约束（永久）**：券核销、积分变动、充值入账等，用唯一索引保证永久只生效一次。
- **请求幂等（短期）**：HTTP 请求用 Idempotency-Key，TTL 24–72 小时，记录 PROCESSING/SUCCEEDED/FAILED。

### 3.2 使用步骤
1. 为每个写操作定义业务唯一键（券+动作、account+biz_type+biz_id、order_id）。
2. 建唯一索引，冲突时读回首次结果。
3. 请求幂等表：scope+key 唯一，状态机，租约防并发。
4. 失败语义：可重试错误不缓存；确定性失败缓存 FAILED。
5. 账务类不能只靠 TTL，必须有永久约束。

### 3.3 检查清单
- [ ] 每个写操作有业务唯一键与唯一索引。
- [ ] 请求幂等有 TTL、状态、租约。
- [ ] 同键不同内容返回 409。
- [ ] 失败结果缓存策略明确。
- [ ] 账务幂等不依赖 TTL。

### 3.4 常见误用
- 只做请求幂等不做业务约束；
- 幂等记录与业务写不同事务；
- TTL 过期后重复入账；
- 并发同键重复执行。

## 4. Transactional Outbox

### 4.1 定义
把「业务数据变更」与「待发送事件」写在同一数据库事务，再由独立 relay/worker 读取 outbox 投递，保证业务成功则事件不丢。

### 4.2 表结构
| 字段 | 说明 |
|---|---|
| event_id | 事件唯一 ID |
| event_type | 事件类型 |
| payload | 事件内容 |
| status | PENDING/PROCESSING/SENT/FAILED |
| attempts | 重试次数 |
| next_retry_at | 下次重试时间 |
| locked_by / locked_until | 领取者与租约 |
| created_at | 创建时间 |

### 4.3 消费流程
1. 业务事务：写业务表 + 写 outbox（PENDING）。
2. worker 原子领取：`findOneAndUpdate({status:PENDING, next_retry_at<=now}, {$set:{status:PROCESSING, locked_by, locked_until}})`。
3. 投递：成功置 SENT；失败退避回 PENDING；超次置 FAILED。
4. 租约过期：清理任务回收 PROCESSING。
5. 失败队列：人工重发；监控积压与失败率。

### 4.4 语义
- 至少一次投递；消费方必须幂等。
- 无法保证严格「恰好一次」；短信等允许极少重复，或用供应商幂等键。

### 4.5 检查清单
- [ ] outbox 与业务写同事务。
- [ ] 有原子领取与租约。
- [ ] 有重试上限、退避、失败队列。
- [ ] 消费方幂等。
- [ ] 有积压/失败监控。
- [ ] 没有「事务外写 outbox」。

### 4.6 常见误用
- 事务外写 outbox；
- 多 worker 无锁重复发送；
- outbox 当消息队列真源；
- 消费失败无限重试不降级。

## 5. Saga（跨聚合/跨服务长事务）

### 5.1 定义
用一系列本地事务加补偿动作替代分布式长事务；分编排（orchestration）与协同（choreography）。

### 5.2 使用步骤
1. 拆长事务为若干本地事务，每个有明确补偿。
2. 选编排或协同；定义状态机与超时。
3. 补偿必须幂等、可重试；补偿失败进人工。
4. 写清「中间状态」对用户/对账的影响。
5. 用故障注入验证每个补偿路径。

### 5.3 检查清单
- [ ] 每个步骤有补偿动作。
- [ ] 补偿幂等、可重试。
- [ ] 有超时与人工兜底。
- [ ] 中间状态有业务说明。
- [ ] 有故障注入用例。

### 5.4 常见误用
- 只有正向流程没有补偿；
- 补偿不幂等；
- 中间状态不可见；
- 补偿失败无人工入口。

---

## 6. 与其他理论关系
- DDD 聚合边界决定事务边界；跨聚合用 outbox/saga。
- CAP/PACELC 决定跨服务一致性取舍；幂等是 outbox/saga 的前提。
- 质量属性场景决定一致性目标（多强、多快）。

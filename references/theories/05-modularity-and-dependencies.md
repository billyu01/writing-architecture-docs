# 模块化与依赖：Parnas / Clean / Hexagonal / 包原则 / Conway

> 用途：把「模块怎么切、依赖怎么指、代码怎么组织」落成可检查的规则。

## 1. Parnas 信息隐藏

### 1.1 定义
模块应按「可能变化的设计决策」切分，把易变细节隐藏在模块内部，而不是按处理步骤切分。

### 1.2 使用步骤
1. 列出系统中最可能变化的点（业务规则、外部协议、存储、算法）。
2. 每个变化点设计一个隐藏边界（接口/抽象）。
3. 模块对外只暴露稳定契约，内部实现可替换。
4. 检查：模块变更是否只影响内部；外部是否依赖了内部细节。

### 1.3 检查清单
- [ ] 每个易变点有隐藏边界。
- [ ] 模块接口稳定、实现可替换。
- [ ] 外部没有依赖内部数据结构。
- [ ] 变化影响范围可评估。

### 1.4 常见误用
- 按技术步骤切模块；
- 接口暴露数据库字段；
- 外部直接读模块内部表。

## 2. 耦合与内聚

### 2.1 定义
内聚：模块内部元素的相关程度；耦合：模块之间的依赖强度。目标高内聚、低耦合。

### 2.2 判断标准
- 高内聚：一个模块只做一件事；变化原因单一。
- 低耦合：依赖少、依赖稳定接口、无环、无双向。

### 2.3 使用步骤
1. 画模块依赖图。
2. 标出双向依赖、环、跨层直连。
3. 用「变化原因」检查内聚：一个模块是否因多个不相关原因变化。
4. 重构：合并/拆分/引入接口/移动职责。
5. 用 ArchUnit/import 规则固化。

### 2.4 检查清单
- [ ] 无环依赖。
- [ ] 无双向依赖。
- [ ] 无跨层直连。
- [ ] 每个模块职责单一。
- [ ] 依赖指向稳定接口。

## 3. Clean Architecture 依赖规则

### 3.1 定义
依赖只能指向内层（实体/用例），不能指向外层（框架/数据库/UI）；外层通过接口反转依赖。

### 3.2 分层
| 层 | 内容 | 依赖 |
|---|---|---|
| 实体 | 业务对象与规则 | 无 |
| 用例 | 应用编排 | 实体 |
| 接口适配器 | 控制器、网关、仓储实现 | 用例 |
| 框架/驱动 | Web、DB、消息 | 适配器 |

### 3.3 使用步骤
1. 把领域模型放最内层，不依赖框架。
2. 用例层编排领域对象，定义端口接口。
3. 适配器实现端口（仓储、外部服务）。
4. 框架层只做装配。
5. CI 检查 import 方向。

### 3.4 检查清单
- [ ] 领域层不 import 框架/DB。
- [ ] 端口接口在领域/用例层，实现在适配器。
- [ ] 依赖方向单向向内。
- [ ] 有自动化检查。

### 3.5 常见误用
- 领域层直接依赖 ORM；
- 控制器写业务规则；
- 仓储接口放在基础设施层。

## 4. Hexagonal（端口与适配器）

### 4.1 定义
应用核心通过端口与外部交互；适配器实现端口（HTTP、DB、消息、第三方）。核心不感知外部技术。

### 4.2 端口类型
- 入站端口：用例接口（HTTP 控制器调用）。
- 出站端口：仓储、消息、外部服务接口。

### 4.3 使用步骤
1. 定义应用核心与用例。
2. 为每个外部依赖定义出站端口。
3. 为每个入口定义入站端口。
4. 写适配器实现，做契约测试。
5. 替换技术时只换适配器。

### 4.4 检查清单
- [ ] 核心不依赖具体技术。
- [ ] 每个外部依赖有端口。
- [ ] 适配器有契约测试。
- [ ] 替换实现不影响核心。

## 5. 包设计原则（Martin）

### 5.1 内聚三原则
- REP 复用发布等价：复用的粒度等于发布的粒度。
- CCP 共同闭包：一起变化的类放一起。
- CRP 共同复用：不一起被复用的类不要放一起。

### 5.2 耦合三原则
- ADP 无环依赖：包依赖不能成环。
- SDP 稳定依赖：依赖指向更稳定的包。
- SAP 稳定抽象：稳定包应更抽象。

### 5.3 使用步骤
1. 按变化原因划包。
2. 画包依赖图，找环。
3. 计算稳定性（传出/总依赖），让依赖指向稳定侧。
4. 稳定包用接口抽象。
5. CI 固化规则。

### 5.4 检查清单
- [ ] 包按变化原因划分。
- [ ] 无环。
- [ ] 依赖指向稳定包。
- [ ] 稳定包有抽象。
- [ ] `common` 不承载业务规则。

## 6. Conway 定律

### 6.1 定义
系统架构会反映组织的沟通结构；团队边界会影响模块边界。

### 6.2 使用步骤
1. 画团队/沟通结构。
2. 对照模块边界：是否一个模块跨多个团队、一个团队维护多个不相关模块。
3. 调整团队或模块边界，使「谁维护」与「怎么切」一致。
4. 跨团队接口写契约与 owner。

### 6.3 检查清单
- [ ] 模块有明确 owner。
- [ ] 团队边界与模块边界不冲突。
- [ ] 跨团队接口有契约。
- [ ] 变更路径清晰。

## 7. 模块化单体 vs 微服务

### 7.1 选择标准
| 维度 | 模块化单体 | 微服务 |
|---|---|---|
| 团队规模 | 小/中 | 多团队 |
| 部署 | 单部署单元 | 独立部署 |
| 事务 | 本地事务简单 | 分布式一致性复杂 |
| 故障隔离 | 弱 | 强 |
| 运维成本 | 低 | 高 |
| 适用 | 业务边界清晰但团队小 | 独立扩缩/团队自治 |

### 7.2 使用步骤
1. 先按上下文模块化，不急着拆服务。
2. 用扩展性/团队/故障隔离需求判断是否需要拆。
3. 拆之前先保证模块边界与依赖规则可检查。
4. 拆分后补分布式一致性、可观测、契约测试。

### 7.3 常见误用
- 为了「先进」直接拆微服务；
- 模块化没做好就拆；
- 拆完没有契约与可观测。

## 8. 与其他理论关系
- Parnas 信息隐藏与 DDD 限界上下文互补：前者切变化点，后者切模型边界。
- Clean/Hexagonal 决定依赖方向；包原则量化稳定性；Conway 决定组织边界；4+1 开发视图承载这些规则。

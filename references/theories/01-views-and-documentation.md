# 视图与文档理论：arc42 / 4+1 / C4 / IEEE 42010 / UML

> 用途：把「架构文档怎么组织、视图怎么切、图怎么画」落成可执行方法。每条理论都给出步骤、产物、检查清单、误用。

## 1. arc42（12 节架构文档模板）

### 1.1 定义与适用
arc42 是面向实践的架构文档模板，用 12 节覆盖「需求与质量、结构与视图、概念/技术/决策」，可按项目裁剪。适用于需要长期维护、多人评审的系统架构文档。

### 1.2 12 节与内容
| 节 | 内容 | 本技能落点 |
|---|---|---|
| 1 引言与目标 | 任务、质量目标、读者 | §1 引言与目标 / 架构摘要 |
| 2 约束 | 技术、组织、法规约束 | §2 架构约束 |
| 3 上下文与范围 | 业务上下文、外部系统、接口 | §3 业务背景 + 系统上下文图 |
| 4 解决方案策略 | 核心技术思路与取舍 | §8 架构决策 + §10 选型 |
| 5 构建块视图 | 静态结构、模块、层次 | §5.1 逻辑视图 + §7 组件清单 |
| 6 运行时视图 | 重要运行时场景、交互 | §5.2 进程视图 + §6 核心流程 |
| 7 部署视图 | 硬件/基础设施/部署映射 | §5.4 物理视图 |
| 8 横切概念 | 安全、可观测、错误处理等 | §11 横切概念 |
| 9 架构决策 | 重要决策与理由 | §8 架构决策 |
| 10 质量要求 | 质量树、质量场景 | §9 非功能需求 |
| 11 风险与技术债 | 已知风险、技术债 | §13 风险与技术债 |
| 12 术语表 | 统一语言 | §14.2 术语与编号索引 |

### 1.3 使用步骤
1. 按 12 节建目录；对每节写一句「本节回答谁的什么问题」。
2. 标注「裁剪项」：不写的节要说明理由（如无部署视图则说明单机）。
3. 每节内容必须可追溯到上游（需求/约束/决策）或下游（模块/测试）。
4. 写完用 1.4 清单自查。

### 1.4 检查清单
- [ ] 12 节都有内容或明确标注「不适用+理由」。
- [ ] 第 1 节有可度量的质量目标。
- [ ] 第 5/6/7 节分别对应逻辑/运行时/部署，不混写。
- [ ] 第 8 节覆盖安全、可观测、错误处理、配置密钥。
- [ ] 第 9 节每条决策有备选与代价。
- [ ] 第 12 节术语与正文用词一致。

### 1.5 常见误用与修正
| 误用 | 后果 | 修正 |
|---|---|---|
| 12 节全填模板话 | 文档很长但无法指导实现 | 每节至少一个具体表/图/判据 |
| 构建块视图写成代码目录 | 读者看不到职责边界 | 先写模块职责/接口/依赖，再附目录 |
| 部署视图写成服务器清单 | 看不出网络与故障域 | 补分区、协议端口、副本、故障转移 |
| 质量要求只写「高性能」 | 无法验收 | 改成质量属性场景（见 03 质量理论） |

### 1.6 出处
arc42 Template Overview: <https://arc42.org/overview/>

## 2. Kruchten 4+1 视图模型

### 2.1 定义与适用
用逻辑、进程、开发、物理四个视图描述系统，再用场景（+1）验证四者自洽。适用于中大型系统、需要多角色评审的架构文档。

### 2.2 五个视图
| 视图 | 回答 | 必备内容 | 常见图 |
|---|---|---|---|
| 逻辑视图 | 系统由哪些构建块组成、职责与依赖 | 模块、接口、依赖方向、不做什么 | 组件图、包图 |
| 进程视图 | 运行时怎么跑、并发与同步 | 进程/线程/协程、异步、事务、锁、失败重启 | 进程图、时序图 |
| 开发视图 | 代码怎么组织、怎么构建测试 | 分层、包、构建、测试分层、本地开发 | 包图、目录树 |
| 物理视图 | 软件到基础设施的映射 | 部署单元、节点、网络、存储、副本 | 部署图 |
| 场景视图 | 关键用例如何穿过前四个视图 | 用例、模块链、验收点、失败路径 | 用例表、时序图 |

### 2.3 使用步骤
1. 先画逻辑视图：按业务能力/上下文切模块，写六项（名称/职责/接口/依赖/不做/承载需求）。
2. 再画进程视图：标同步/异步、事务边界、锁与租约、失败恢复。
3. 再画开发视图：给目录、依赖规则、构建与测试分层。
4. 再画物理视图：部署单元、分区、协议端口、副本与故障域。
5. 最后用场景视图逐条走：每个核心用例经过哪些模块、在哪失败、如何验收。
6. 四视图之间做一致性检查：逻辑模块是否都能在开发视图找到；部署单元是否覆盖所有运行时组件。

### 2.4 检查清单
- [ ] 五视图齐全，缺一不算完整。
- [ ] 逻辑视图每个模块有六项。
- [ ] 进程视图有同步/异步边界、事务、失败恢复。
- [ ] 开发视图有依赖方向与测试分层。
- [ ] 物理视图有节点、副本、协议端口、故障域。
- [ ] 场景视图至少覆盖 4 个核心用例，并指向前四视图。

### 2.5 常见误用
- 只画逻辑+物理，缺进程/开发/场景；
- 进程视图画成部署节点；
- 场景视图写成用例列表，不验证视图；
- 逻辑视图一个框里堆模块名。

### 2.6 出处
Kruchten, P. (1995). The 4+1 View Model of Architecture. IEEE Software.

## 3. C4 模型

### 3.1 定义与适用
用 Context / Container / Component / Code 四层加 Deployment 图描述架构，按读者关注点分层展示。适用于需要向不同角色（业务、开发、运维）解释系统。

### 3.2 四层与部署
| 层 | 回答 | 元素 | 本技能落点 |
|---|---|---|---|
| Context | 系统与外部角色/系统的关系 | 人、系统、外部系统、协议 | 图 4-1 系统上下文 |
| Container | 有哪些可部署单元/进程 | Web 应用、服务、数据库、队列 | 逻辑/进程/部署视图 |
| Component | 容器内有哪些模块 | 组件、接口、依赖 | 逻辑视图模块表 |
| Code | 类级结构（通常不画） | 类、接口 | 领域模型/类图 |
| Deployment | 容器如何映射到基础设施 | 节点、部署单元、网络 | 图 5-4 部署图 |

### 3.3 使用步骤
1. 先画 Context：只画系统边界、外部角色、外部系统、协议；不画内部模块。
2. 再画 Container：每个可部署单元一个容器，标职责、技术、存储。
3. 需要时画 Component：只画关键容器内部模块，标接口与依赖。
4. Deployment 图：容器到节点/分区的映射，标协议与副本。
5. 每层只回答一个问题，不跨层混画。

### 3.4 检查清单
- [ ] Context 图无内部模块。
- [ ] Container 图每个容器有职责与技术。
- [ ] Component 图只画关键容器，不画全量类。
- [ ] Deployment 图有节点、分区、协议、副本。
- [ ] 层与层之间关系可追溯（Context 的系统 → Container 的容器）。

### 3.5 常见误用
- Context 里画内部模块；
- Container 和 Component 混在一张图；
- 部署图把代码层（repository/service）当容器；
- 图没有图例，读者不知道形状含义。

### 3.6 出处
C4 model: <https://c4model.com/>

## 4. IEEE 42010（视点与视图）

### 4.1 定义与适用
规定架构描述应围绕利益相关者、关注点、视点、视图及对应关系组织。适用于需要证明「文档覆盖了所有相关方关注点」的评审场景。

### 4.2 核心概念
- **利益相关者**：关心系统的人/角色（业务、开发、测试、运维、安全、财务）。
- **关注点**：他们关心的问题（功能、性能、安全、可维护性、成本）。
- **视点**：观察架构的角度（逻辑、进程、部署、数据、安全）。
- **视图**：按视点产出的模型（图/表）。
- **对应关系**：视图之间的一致性规则（模块↔部署↔场景）。

### 4.3 使用步骤
1. 列利益相关者与关注点表。
2. 为每类关注点选视点，定义视图产物。
3. 写视图之间的对应规则（如每个逻辑模块必须落到至少一个部署单元）。
4. 检查每个关注点至少被一个视图覆盖。
5. 文档开头写读者分层与阅读路径。

### 4.4 检查清单
- [ ] 有利益相关者/关注点表。
- [ ] 每个关注点有对应视图。
- [ ] 视图间有一致性规则并可检查。
- [ ] 文档有读者分层与阅读路径。

### 4.5 常见误用
- 一套视图给所有读者；
- 视图之间没有对应关系；
- 文档不说明「谁该看哪节」。

### 4.6 出处
IEEE 42010（Systems and software engineering — Architecture description）。

## 5. UML（类图/组件图/部署图/时序图/状态机）

### 5.1 定义与适用
标准建模语言，提供类、组件、部署、时序、状态机等图的语法。架构文档只用其中一小部分，但符号必须标准。

### 5.2 图种与用途
| 图 | 用途 | 本技能落点 |
|---|---|---|
| 类图 | 聚合/实体/值对象/关系/基数 | 核心领域模型、DDD 概念图 |
| 组件图/包图 | 模块、接口、依赖 | 逻辑视图、开发视图 |
| 部署图 | 节点、制品、通信路径 | 物理部署 |
| 时序图 | 生命线、消息、片段 | 核心流程 |
| 状态机 | 状态、迁移、守卫 | 券/充值单/导入批次 |

### 5.3 使用步骤
1. 选对图种：静态结构用类/组件/部署；行为用时序/状态机。
2. 统一符号：箭头方向、实线/虚线、基数写法、构造型（«aggregate root» 等）。
3. 只画关键元素：类图不堆全量字段；时序图生命线 ≤5；状态机只画合法迁移。
4. 图与正文互链：图号、图注、索引。

### 5.4 检查清单
- [ ] 图种与问题匹配。
- [ ] 符号标准、全文档一致。
- [ ] 类图有基数与关系。
- [ ] 时序图有事务/异步边界与异常分支。
- [ ] 状态机有守卫条件与非法迁移行为。

### 5.5 常见误用
- 自造箭头/形状；
- 时序图箭头向上；
- 部署图把进程内模块画成节点；
- 状态机没有守卫与终止态。

### 5.6 出处
OMG UML 规范。

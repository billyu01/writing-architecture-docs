# 质量属性与验证：ISO/IEC 25010 / ATAM / SRE / Fitness Function

> 用途：把「高性能、高可用」这类口号变成可设计、可验收的质量要求；给出质量场景、权衡分析、SLO 与自动化验证的完整方法。

## 1. ISO/IEC 25010 质量模型

### 1.1 定义
ISO/IEC 25010 把软件质量分为 8 个特性、若干子特性，用于系统化识别质量要求，避免只盯性能。

### 1.2 八个质量特性
| 特性 | 含义 | 典型指标 |
|---|---|---|
| 功能适合性 | 功能是否满足需求 | 功能覆盖率、正确率 |
| 性能效率 | 时间行为、资源利用 | P95/P99 延迟、吞吐、CPU/内存 |
| 兼容性 | 与其他系统/环境共存 | 协议兼容、版本兼容 |
| 易用性 | 用户使用成本 | 任务完成率、错误率 |
| 可靠性 | 可用性、容错、可恢复 | 可用性、MTTR、RPO/RTO |
| 安全性 | 保密、完整、抗抵赖、可审计 | 越权率、漏洞数、审计覆盖 |
| 可维护性 | 模块化、可分析、可修改、可测试 | 变更前置时间、回归缺陷率 |
| 可移植性 | 可安装、可替换、可适配 | 环境迁移成本 |

### 1.3 使用步骤
1. 从 8 个特性里挑本项目真正重要的 3–5 个（不要全选）。
2. 每个特性落到 1–2 个可测子特性。
3. 每个子特性写指标、目标值、测量方法、失败表现。
4. 与需求编号、验收点建立追溯。

### 1.4 检查清单
- [ ] 质量目标不超过 5 个，且都能测。
- [ ] 每个目标有指标、目标值、测量窗口、数据来源。
- [ ] 质量目标能追到需求与验收。
- [ ] 没有「高性能/高可用」这类无度量表述。

### 1.5 常见误用
- 把质量模型当清单全填；
- 指标没有测量方法；
- 只写平均值不写分位；
- 目标值与容量/成本不匹配。

### 1.6 出处
ISO/IEC 25010（SQuaRE 质量模型）。

## 2. 质量属性场景（Quality Attribute Scenario）

### 2.1 定义
用「刺激源 → 刺激 → 环境 → 制品 → 响应 → 响应度量」六部分描述一个可验收的质量场景。它是 ATAM 的输入，也是非功能需求的最小完整单元。

### 2.2 六要素
| 要素 | 要写什么 | 例子 |
|---|---|---|
| 刺激源 | 谁/什么触发 | 店员、定时任务、MongoDB 主节点 |
| 刺激 | 发生什么 | 提交核销请求、主节点切换 |
| 环境 | 什么状态下 | 正常、峰值、降级中 |
| 制品 | 哪个部分受影响 | 核销链路、积分账户 |
| 响应 | 系统怎么反应 | 成功/拒绝/重试/降级 |
| 响应度量 | 怎么算达标 | P95≤300ms、错误率≤0.1%、RTO≤30min |

### 2.3 使用步骤
1. 为每个关键质量目标写 1–3 个场景。
2. 场景必须是「可判真假」的句子，不能是愿望。
3. 把场景映射到设计决策（哪些机制支撑它）。
4. 把场景映射到验收方式（压测/故障注入/监控）。
5. 场景间冲突时做权衡（见 ATAM）。

### 2.4 示例（核销延迟）
- 刺激源：店员；刺激：提交核销；环境：峰值 20 QPS/店；制品：核销接口；响应：返回结果；度量：P95≤300ms、错误率≤0.1%、失败可重试。

### 2.5 检查清单
- [ ] 每个场景六要素齐全。
- [ ] 度量有单位、窗口、数据来源。
- [ ] 场景能追到设计机制与验收用例。
- [ ] 冲突场景有取舍说明。

### 2.6 常见误用
- 只有「响应快」没有度量；
- 场景只写正常路径，不写降级/故障；
- 场景与设计机制脱节。

## 3. ATAM（Architecture Tradeoff Analysis Method）

### 3.1 定义
SEI 的架构权衡分析方法：用质量属性场景评估架构，识别敏感点、权衡点、风险与非风险，输出改进建议。

### 3.2 核心概念
- **敏感点**：某个质量属性对某个设计参数敏感（如副本数影响可用性）。
- **权衡点**：一个参数同时影响多个质量属性（如强一致 vs 延迟）。
- **风险**：可能不达标的决策；**非风险**：已验证的决策。
- **效用树**：质量目标 → 场景 → 优先级。

### 3.3 步骤
1. 建效用树：业务驱动 → 质量属性 → 场景，按重要性排序。
2. 讲架构：按视图讲设计决策。
3. 映射场景到架构：标敏感点/权衡点。
4. 分组讨论：识别风险、非风险、权衡点。
5. 输出报告：风险清单、改进建议、优先级。
6. 复审：改完后按同一场景复验。

### 3.4 产物
- 效用树；
- 场景-决策映射表；
- 风险/非风险/权衡点清单；
- 改进建议与优先级。

### 3.5 检查清单
- [ ] 有质量目标与场景优先级。
- [ ] 每个关键决策标了敏感点/权衡点。
- [ ] 风险有影响与缓解措施。
- [ ] 改进建议有负责人与时点。

### 3.6 常见误用
- 只做一次评审不复审；
- 场景没有优先级；
- 把风险写成「待观察」；
- 评审结论不落到文档与决策记录。

### 3.7 出处
SEI ATAM（Architecture Tradeoff Analysis Method）。

## 4. SRE：SLI / SLO / 错误预算

### 4.1 定义
用可测量的服务水平指标（SLI）定义目标（SLO），用错误预算管理发布风险与稳定性投入。

### 4.2 核心概念
- **SLI**：可测指标（成功率、延迟分位、吞吐）。
- **SLO**：SLI 的目标值 + 统计窗口（如 30 天成功率 ≥99.9%）。
- **错误预算**：1 - SLO；预算耗尽则冻结高风险发布。
- **可观测性**：日志、指标、追踪三支柱。

### 4.3 使用步骤
1. 为每个关键链路定义 SLI（请求成功率、P95 延迟、任务积压）。
2. 定义 SLO 与统计窗口。
3. 定义告警：快烧（短窗口高错误率）与慢烧（长窗口趋势）。
4. 定义错误预算策略：耗尽时暂停发布、优先修复。
5. 把 SLI/SLO 写进非功能章节与运维手册。

### 4.4 检查清单
- [ ] 每个核心链路有 SLI。
- [ ] SLO 有目标值、窗口、数据来源。
- [ ] 有告警阈值与处置。
- [ ] 有错误预算策略。
- [ ] SLO 与容量模型一致。

### 4.5 常见误用
- 只有延迟没有成功率；
- SLO 没有窗口；
- 告警没有处置；
- 错误预算从不触发。

### 4.6 出处
Google SRE Book（Embracing Risk / SLO 章节）。

## 5. Fitness Function（架构适应度函数）

### 5.1 定义
把架构约束写成自动化检查，持续验证架构是否漂移；属于进化架构的核心实践。

### 5.2 常见形式
- 依赖方向检查（ArchUnit、import 规则）；
- 契约测试（Pact）；
- 性能/容量回归；
- 安全扫描；
- 图/文档一致性检查；
- 配置/基础设施策略检查。

### 5.3 使用步骤
1. 把每条硬约束翻译成可执行检查。
2. 放进 CI，失败即阻断。
3. 定期评审检查是否仍对应真实约束。
4. 约束变化时同步更新检查。

### 5.4 检查清单
- [ ] 每条硬约束有对应检查。
- [ ] 检查在 CI 中执行并阻断。
- [ ] 检查失效时有告警。
- [ ] 检查与文档约束同源。

### 5.5 常见误用
- 约束只写在文档里；
- 检查太慢被跳过；
- 检查与真实约束脱节。

### 5.6 出处
Ford, Parsons, Kua. Building Evolutionary Architectures.

## 6. 与其他理论关系
- ISO 25010 提供质量分类；质量场景把分类变成可验收单元；ATAM 做权衡；SRE 把运行期质量变成 SLI/SLO；fitness function 把约束变成持续验证。
- 与 4+1：场景视图是质量场景的载体；与 DDD/一致性：质量目标约束聚合与事务设计。

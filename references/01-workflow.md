# 01 · 完整工作流（11 阶段）

> 读法：每个阶段固定五元组——**输入 / 动作 / 产物 / 完成判据 / 返工信号**。
> 按顺序走，但顺序可调：若调整章节或阶段顺序，必须在文档里显式写出理由，并保证读者理解路径顺畅。
> 经验顺序（被真实用户反复纠正后收敛）：业务分析 → 领域建模 → 逻辑架构 → 组件清单 → 核心流程 → 物理部署 → 决策 → 功能/非功能 → 选型 → 安全 → 扩展。

---

## 阶段 1 · 接单与范围切分

- **输入**：用户原始消息（照抄，不概括）；仓库现状；用户提到的往期需求/聊天记录。
- **动作**：
  1. 把用户原文逐条抄成清单，保留「可能没有」「看下是否满足」这类不确定表述。
  2. 标注三类：需求 / 参照材料 / 硬约束。
  3. 划出本次交付物（几份文档、什么格式、要不要图、要不要 HTML）。
  4. 明确「这次不做什么」。
- **产物**：需求原文清单、交付物清单、范围外清单。
- **完成判据**：用户能在一屏内看到「你要我做什么」与「我这次交什么」，且没有遗漏任何一条原话。
- **返工信号**：把用户的疑问句当需求做；把往期聊天记录直接当已定需求（未逐条给结论）。

## 阶段 2 · 事实基线勘察

- **输入**：代码仓库、既有文档、git 历史、上游依赖、本机/目标环境。
- **动作**：
  1. 列既有文档清单，读上一版架构/需求/决策台账。
  2. 读 git 历史，确认最近改动与提交顺序。
  3. 对上游依赖做**实读**：版本 tag、模型清单、配置行数、扩展点；不采信博客与旧笔记。
  4. 实测环境：端口、数据库、架构、包管理器版本。
  5. 每条事实写成「事实 / 依据」两列。
- **产物**：事实基线表（独立成节，通常放 §0）；上游依赖事实索引（放选型附录）。
- **完成判据**：每条事实有命令输出或文件行号；同一事实全文只有一种说法。
- **返工信号**：出现「应该是」「据说」；两份文档对同一数字/名称说法不同。

## 阶段 3 · 澄清与方案比选

- **输入**：事实基线；需求中的模糊点。
- **动作**：
  1. 先给一段「我已掌握什么」的摘要，让用户能纠正误解。
  2. 提 2–4 个方向性问题，每题 2–3 个选项 + 推荐 + 代价 + 可逆性。
  3. 用户回答后写裁定台账（编号 + 日期 + 原话摘要 + 影响面）。
  4. 对整体路线给 2–3 个方案对比表（形态/强度/契合度/代价），明确推荐。
  5. 把裁定写进长期目标或项目硬约束，防止长会话跑偏。
- **产物**：方案对比表、裁定台账、待决策清单（分类：范围口径 / 产品取舍 / 外部方 / 已裁定可否决 / 已关闭）。
- **完成判据**：所有阻塞设计的问题都有用户口径；没有口径的进清单并写明默认走法。
- **返工信号**：用户答「不考虑，先做 X」——说明问题问错了层次；答非所选——重切问题，不要重复追问。

## 阶段 4 · 需求规格（PRD）

- **输入**：需求原文清单、裁定台账、事实基线、上一版 PRD。
- **动作**：
  1. 开头写清权威顺序、编号方案、优先级机械判据、归属期。
  2. 写现状基线（实测，不引用旧文档结论）。
  3. 写「架构约束（违反即失效）」——后面所有设计的红线。
  4. 按能力族写 FR：每条带可验证的一句话 + 优先级 + 归属期 + 状态 + 量化契约 + 溯源。
  5. 写 NFR、GATE（验收关卡：判据 + 验证方式）、OOS（明确范围外）、OPEN（待决，给默认走法）。
  6. 写分期映射表、往期需求追溯表（覆盖/部分/未覆盖，逐条结论）、与上一版差异表。
  7. 附录写用户裁定溯源。
- **产物**：PRD 一份（含上述各块）。
- **完成判据**：每条需求能对应到验收关卡或验证方式；往期需求逐条有结论；引用的编号在文档内真实存在。
- **返工信号**：用户说「不够全量、逻辑不清晰」；大量「沿袭旧文档第 X 节」导致无法独立阅读；引用了不存在的 GATE。

## 阶段 5 · 业务分析 → 领域建模

- **输入**：PRD §1/§2；现有数据集合；用户对业务的纠正。
- **动作**：
  1. 业务分析：业务定位、价值链分阶段、优先级分层、用户画像、商业模型。
  2. 领域建模：实体清单 + 关系 + 生命周期 + 不变量。
  3. 画实体关系图。
  4. 写「领域概念速览表」（域 / 主体 / 一句话说明）。
  5. 标注哪些是过程数据（不是真源）。
- **产物**：业务分析节、统一语言、限界上下文与聚合、实体/值对象表、领域事件表、生命周期与状态、不变量、仓储/领域服务、ER 图（仅作数据模型子节）。
- **完成判据**：每个实体对到一个真实数据集合；每个业务阶段对到一张图或一张表；过程数据与业务真源分开；聚合根/领域事件/不变量/仓储齐全——**ER 图不能替代领域建模**。
- **返工信号**：顺序错（先画架构再补业务）；实体表里出现没有对应集合的「概念实体」。

## 阶段 6 · 架构视图与技术决策

- **输入**：PRD 约束节；领域模型；技术选型。
- **动作**：
  1. **4+1 五视图齐全**：逻辑（每个模块写清名称/职责/对外接口/依赖方向/不做什么/承载需求）、进程（进程树、并发、异步、事务边界、锁、失败重启、容量）、开发（目录、分层、构建、测试分层、本地开发）、物理（部署形态逐形态画）、场景（用例 → 模块链 → 验收点）。
  2. 决策表：每条决策必须有「备选方案」与「代价/推翻条件」两列，编号稳定（D1…Dn）可被其他文档引用。
  3. 一处只讲一件事：需求判定去 PRD，细节去模块分册，总览只留摘要 + 链接。
- **产物**：视图文档或总览对应章节、决策编号表。
- **完成判据**：任何技术选择能指到 D 编号；物理视图与部署清单、真实环境一致；没有「没有备选的决策」。
- **返工信号**：决策只写结论；视图里出现「待定」却不进 OPEN 清单。

## 阶段 7 · 技术选型与可行性验证

- **输入**：阶段 2 的上游事实；阶段 6 的决策；打包/发布渠道。
- **动作**：
  1. 选型结论一张表（层 / 选型 / 备注）。
  2. 裁剪或配置清单：禁用/保留/新增，每条可数（禁 N 行 / 插 M 行）。
  3. 集成契约：谁调用谁、子进程还是服务、凭据怎么进。
  4. 版本钉选：实测发布渠道，写清「哪个版本可用、哪个不可用」。
  5. 附录写事实索引（本次实读了哪些文件）。
- **产物**：技术选型文档、配置/补丁工件、版本钉选表。
- **完成判据**：每个「用某版本」有实测来源；裁剪清单行数与上游快照逐行对得上；能回答「升级时怎么改」。
- **返工信号**：配置行标识与上游快照对不上；「最新版」在发布渠道落后两个版本。

## 阶段 8 · 模块详细设计

- **输入**：架构总览、PRD 的 FR/NFR/GATE、现有代码结构。
- **动作**：
  1. 先写母本定死模板（每模块固定几段），母本通过后再拆册。
  2. 每册必须有：定位与「不做什么」、能力→需求→验收对照表、流程与时序、接口与返回形状、交互协议、数据/状态设计、错误分类、验收门禁（含「改坏什么必须红」的变异实验）、依赖与 `文件:行号` 锚点、实现状态与差距。
  3. 每册头部写「上位文档」与状态。
- **产物**：模块详设母本、`modules/NN-*.md` 分册。
- **完成判据**：每册可独立阅读；册与册职责不重叠；总览组件清单能逐个链接到分册；锚点指向真实位置。
- **返工信号**：用户说「很松散」（组件没有层级、模块边界不清）；总览组件数与分册数不一致；引用文件已改名。

## 阶段 9 · 整合总览与配图

- **输入**：前述全部文档；已有图资产；配图技能。
- **动作**：
  1. **图盘点**：逐张判定复用/新建/存档；复用图必须注明与当前设计的 delta。
  2. 新建图按类型分派（ER、核心流程时序、物理部署各一张），统一风格总纲与画布预算。
  3. 总览按「基线→概述→业务分析→领域→逻辑→组件清单→流程→物理→决策→功能非功能→选型→安全→扩展→附录」组织。
  4. 组件清单一律三层：层 → 组件 → 子组件（文件/操作级）。
  5. 图**内嵌**进文档（不要只给链接）；每图给编号 + 一句图注 + 交互源 + 矢量文件链接。
  6. 附录写图资产索引表。
  7. 若声明「可重建」，构建脚本与模板必须真的在仓库里，并跑一次验证；**重建命令写进 README/运维文档，不写进架构正文**。
- **产物**：架构总览（Markdown 源 + 可视版 HTML）、图资产目录、图索引表。
- **完成判据**：打开文档不点链接即可看到全部图；每图有编号、图注、源文件；组件清单可逐层下钻；图索引与 assets 目录一一对应。
- **返工信号**：用户说「图没法直接看到」「有上下左右滚动」「图叠加了」「文字超过框图」；声明可重建但脚本已不存在。
- **详细做法**：转 `references/diagrams/`（配图规范）。

## 阶段 10 · 整体检查验收与定稿

- **输入**：用户本轮全部要求（原文）；全部文档与图。
- **动作**：
  1. 写设计符合性检查报告：用户每条要求一行，给证据（文件/行）与判定。
  2. 做文档-代码漂移核查：抽查锚点、状态表述、数量断言。
  3. 统一权威顺序表与修订史。
  4. 旧文档头部加「已被部分取代 + 新文档链接」横幅（原文不删）。
  5. 台账类文档只追加注解，不改历史条文。
  6. 跑机器检查脚本，再找独立评审；修复后逐条复核。
- **产物**：检查报告、修订史、取代横幅、权威顺序表、复验记录。
- **完成判据**：用户每条要求都有判定行；旧文档都能顺横幅找到新权威；修订史有日期与一句变更；没有两套并存的权威顺序；机器检查 0 error。
- **返工信号**：用户直接问「都正常吗？任务完成了吗？」——说明验收没做或没给证据。

## 阶段 11 · 转入实施计划

- **输入**：PRD、架构总览、模块分册、技术选型。
- **动作**：
  1. 用计划类技能（如 `writing-plans`）。
  2. 头部写 Goal / Architecture / Tech Stack / Spec 四段。
  3. 写 Global Constraints：测试规矩、错误分类冻结、数据不变量、文件所有权、分支与提交约定、单进程跑测。
  4. 每个任务给步骤级测试代码与验收命令。
  5. 收口节写完成判据；自审节写覆盖性/占位符/类型一致性自查。
- **产物**：实施计划、任务与文件所有权矩阵。
- **完成判据**：每个任务的文件集两两不相交、可并行分派；计划里的每个路径都真实存在；收口判据可机械执行。
- **返工信号**：计划里写了不存在的测试路径；任务边界交叉导致两个执行者改同一文件。

## 跨阶段纪律

1. **返工不等于重做**：先判断问题属于内容层（写错）、结构层（顺序/层级错）、渲染层（图/样式/尺寸）还是资产层（源文件/链接错），只改对应层。
2. **每次被打回都升级检查器**：用户指出的新症状，必须变成一条可重复执行的检查，而不是只修这一次。
3. **顺序可调但要留痕**：改章节顺序时，同步改目录、锚点、图索引与交叉引用，并在修订史写明原因。
4. **长会话防漂移**：把已确认裁定写成项目级硬约束（如仓根 `AGENTS.md`），下一轮先读它。
5. **正文不写裸代号**：需求/验收/决策用中文名称；必须编号时首次出现写全称+解释，编号只放附录索引。
6. **单文件单写者**：并行写文档/图时一个文件同一时间只允许一个写者；收口后主控统一重建并比对哈希。

# 03 · 质量校验、修复回路与评审分工

## 1. 六个质量维度（按顺序判）

判定顺序有讲究：**先完整 → 再一致 → 再可追溯 → 再可执行 → 再可维护 → 最后决策留痕**。前一项不过，后一项的结论都不可信。

### 1.1 完整性

- **合格**：读者只靠文档能回答六个问题——有哪些部分、各负责什么、数据在哪些存储、请求怎么走、部署几个单元、出问题看哪里。每个对外能力有落点，每个非功能要求有归属。
- **查法**：需求清单 ↔ 文档章节**双向**反查（只走一个方向会漏）。
- **症状**：模块清单有名字但正文没讲；讲了流程没讲部署；有安全章节但没写信任边界；「其余见另一份」而那份已作废。

### 1.2 一致性（四个独立方向）

1. **跨文档**：架构/需求/分册/计划之间，同一事实（数量、路径、状态）同一值。
2. **图文**：图上的节点、连线、标注与正文一致；图注数字与图内文字一致。
3. **文档-代码**：常量、集合名、状态数、函数位置真实存在且相等。
4. **术语**：同一个东西只有一个名字；一处改名，全仓同步。

**查法**：挑出「事实型断言」（数字、枚举、路径、状态词），逐条列唯一来源后机械核对。数量断言优先怀疑——「按行数算」和「按名字算」是两种口径，不是两种观点。

### 1.3 可追溯

- **合格**：三条链完整——需求→设计→验收点；设计→依据（代码/实验/裁定/外部文档）；结论→证据（命令输出/文件行号/提交号）。
- **查法**：每条「因为所以」问依据；每个需求问「谁验、怎么验、在哪验」。答不出来就标「未核」，不许用「显然」补。
- **症状**：验收点没人认领；依据是已删除的临时目录；数字断言没有实测日期；需求外推到后续阶段但权威文档没标。

### 1.4 可执行

- **合格**：每条硬约束能翻译成「实现必须怎样、违反时哪条用例会红」；每个验收点有判据、阈值来源、失败路径（重试/降级/终止）。
- **查法**：把约束改写成一句可判真假的话，再问「哪个脚本/用例能判它」。改不出来=愿景；判据没人执行=形同虚设。
- **症状**：「必须保证可靠」这类无法判真假的句子；判据恒为未知；裸计数判据（换成员仍能骗过）；验收点没有调用方。

### 1.5 可维护

- **合格**：权威顺序、修订史、图/资产索引、重建脚本四件齐备且真实可跑。
- **查法**：按权威顺序从高到低读；按修订史抽查落点；按索引逐个点开；**真跑一次重建命令**比对 diff。
- **症状**：多份文档自称权威；生成物被手改；重建命令写着但脚本不存在；作废内容被删；行号锚点整体漂移数十处。

### 1.6 决策留痕与可恢复

- **合格**：每个改方向的决策有原文、落点、作废清单、恢复手段；被作废的不删除，标注时间与理由。
- **查法**：裁定原文→硬约束落点→受影响处逐处标注→作废清单→恢复命令，五件套逐项核对。
- **症状**：改文档不留原因；作废分支/目录删了没登记提交号；为了「历史干净」删旧描述；时点性文档被顺手改成新结论。

## 2. 机器可查清单

每次评审建一个证据目录，命令原文与输出一起存；否则「查过了」无法复核。检查前先记录**基线提交 + 工作树状态**。

| # | 检查项 | 动作 | 通过条件 |
|---|---|---|---|
| M1 | 内部链接可达 | 抽全文链接目标逐个解析 | 破链 = 0 |
| M2 | 图资产三件套 | 按图索引查 HTML/SVG/PNG | 每图至少一种可视格式存在 |
| M3 | 生成物可重建 | 运行文档声明的重建命令，比对 diff | 命令存在可执行，diff 仅预期改动 |
| M4 | 行号锚点有效 | 对 `file:line` 取实际行内容，人工抽检语义 | 可定位锚点命中率 100% |
| M5 | 数量断言自洽 | 每个数字找唯一来源并复算 | 全仓一个值 + 复算命令 |
| M6 | 枚举断言逐名相等 | 集合相等（注册集==声明集==文档清单） | 差集为空 |
| M7 | 术语唯一 | 建术语表，grep 同义词与旧名 | 旧名只出现在「已作废」标注中 |
| M8 | 路径存在性 | 仓库内路径逐个校验 | 不存在 = 0；历史路径带「已不存在」标注 |
| M9 | 状态词与事实对齐 | 「未实现/未合并/未提交/不存在」逐个核 | 状态词有当日证据 |
| M10 | 版本与依赖 | 版本号与锁文件/镜像标签比对 | 三处一致 |
| M11 | 配置项真实存在 | 文档提到的配置键在定义处存在 | 未定义键 = 0 |
| M12 | 用例计数 | 跑 `--collect-only` 或等价命令 | 精确相等，不接受「大约」 |
| M13 | 图内文字不溢出 | 文字宽度 vs 框宽、端点 vs 节点边界 | 溢出 0、悬空 0 |
| M14 | 多图样式隔离 | 内嵌多图时 id/class 是否加图前缀 | 无重复 id；class 不冲突 |
| M15 | 敏感信息不入仓 | 凭据格式与常见键名全仓检索 | 命中 0 |
| M16 | 不引用被忽略目录 | grep 临时目录/草稿目录路径 | 活引用 = 0 |
| M17 | 门禁不被畸形值骗过 | 长度/格式/枚举校验，不只比相等 | 畸形值无法让断言变绿 |
| M18 | 未提交改动 | 评审前跑 `git status` 并写进报告 | 基线提交 + 工作树状态明确 |
| M19 | 4+1 视图完整 | 扫 H2/H3 标题是否含逻辑/进程/开发/物理/场景视图 | 缺进程/开发/场景视为不合格 |
| M20 | 领域建模要素 | 领域节是否含聚合/值对象/领域事件/生命周期/不变量/仓储 | 缺项即退回；ER 不能替代 |
| M21 | 代号纪律 | 扫 FR/GATE/D 等代号；查是否有编号说明章节、标题是否裸代号 | 正文优先中文名；编号必须有解释 |
| M22 | 写作边界 | 扫重建/构建命令（build_template/embed_svg/重建命令等） | 出现在架构正文即不合格 |
| M23 | 章节深度 | 功能/选型/安全/扩展四节内容行数 | 过少（一句话）即退回扩写 |

> 现成脚本：本技能 `scripts/check_architecture_docs.py` 覆盖 M1/M2/M3(部分)/M4/M8/M14/M16；配图脚本覆盖 M13/M14/M17(部分)。其余需项目内补。

## 3. 人判断清单

| # | 检查项 | 看什么 | 证据形式 |
|---|---|---|---|
| H1 | 业务定位 | 客户是谁、平台角色是什么、边界在哪 | 一句话定位 + 逐处引用口径一致 |
| H2 | 决策合理性 | 备选、为什么选、代价、推翻条件 | 决策表每行四列 |
| H3 | 隐藏取舍 | 有没有为了好看合并/省略，风险去哪了 | 「降级项 + 补偿机制 + 负责人」清单 |
| H4 | 图表达 | 不看正文能否读懂；层级是否真分层 | 图 + 一句「它回答什么问题」 |
| H5 | 章节顺序 | 读者理解路径是否顺畅 | 目录 + 一句排序理由 |
| H6 | 粒度 | 该聚合的聚合、该细分的细分 | 组件清单两层可下钻 |
| H7 | 验收点可达成 | 判据来源、阈值、失败路径是否闭合 | 每点三行：判据/来源/失败路径 |
| H8 | 需求覆盖口径 | 「核心需求」是否包含安全、审计、合规 | 口径声明 + 两种口径分别结论 |
| H9 | 迁移与回滚 | 数据/接口迁移步骤、双写窗口、回滚条件 | 迁移映射表 + 回滚命令 |
| H10 | 证据诚实 | 未核项是否标了「未核」 | 「证据不足」单列一节 |
| H11 | 文档形态 | 该给图的地方有图，该可 diff 的是文本 | 载体分工说明 |
| H12 | 交付可验证 | 用户按文档能否自己复现验证 | 验证命令 + 预期输出 |
| H13 | 逻辑视图模块内容 | 每个模块是否写清职责/接口/依赖/不做/承载需求 | 模块卡片或表逐项检查 |

## 4. 修复回路（六步，不许跳步）

```
① 定位（可复现） → ② 分级（P0/P1/P2） → ③ 修改（最小改动）
→ ④ 复核（没参与修改的人） → ⑤ 回写（文档/索引/修订史/台账） → ⑥ 复验（同一套检查重跑）
```

| 步 | 动作 | 产出 |
|---|---|---|
| ① 定位 | 用同一套脚本复现；记录基线提交、工作树状态、命令原文 | 问题条目：现象 + 命令 + 输出 + 文件行号 |
| ② 分级 | P0=让验收失效或产生假绿；P1=结论失真但可带条件接受；P2=登记后接受 | 分级表 + 每级处置方式 |
| ③ 修改 | 只改被点名的位置；不改技术判断；diff 逐条对应问题编号 | diff |
| ④ 复核 | 复核者只读，结论只有三种：已处理/未处理/新问题 | 复核表 |
| ⑤ 回写 | 修订记录、作废标注、台账增量、索引与计数同步 | 修订记录 + 台账 |
| ⑥ 复验 | 重跑①全部检查，确认归零且无新问题 | 前后对比表 |

### 4.1 批量漂移回写（文档-代码不一致时）

1. 先归纳模式（例：插块导致整段行号偏移 / 另一文件小幅偏移 / 状态陈述过时 / 数量小修），每类给根因；模式化后几百处变成几件可核对的事。
2. 完成判据先写死：每类都处理、每册头部记修订、只改行号与状态词、不得改技术判断。
3. 改前查并发：先取最新工作树；与并行改动冲突时先对齐再改。
4. 改完例行统计：每册增/删行数 + 合计。
5. 带回新事实：批量过程发现先前判断不精确的（如「+25 行」实际「+36 行」），显式写进报告，不悄悄改。

### 4.2 防再犯（按性价比）

1. 锚点少用绝对行号，优先「文件 + 符号名」。
2. 生成物永不手改，全部由脚本重建。
3. 门禁用集合相等，不用计数。
4. 断言要能挡畸形值（长度、格式、枚举）。
5. 状态词必须带当日证据。
6. 同一事实只允许一个权威来源，其余引用不复制。

## 5. 评审角色与分工

| 角色 | 查什么 | 不查什么 | 证据形式 |
|---|---|---|---|
| 作者自检 | 结构、链接、计数、锚点、已知差距 | 不下「合格」结论 | 自查清单 + 未解决项 |
| 独立评审 | 单模块/单任务的判据、契约、测试是否有牙齿 | 不查跨模块整合风险 | 分级问题表 + 通过/不通过 |
| 全分支终审 | 跨文档一致性、集成风险、架构符合性、漂移 | 不查单任务细节 | 三态结论 + 裁定列表 |
| 修复复核 | 每条问题是否真处理、有无新问题 | 不重新审全量设计 | 逐条状态表 + 新证据 |

硬规则：
1. 评审者与作者不同人/不同代理，评审者**只读**；
2. 评审包必须含基线提交、完整 diff、对应需求条目，不把作者结论当输入；
3. 复核由**没参与修改**的人做，修改者不能自己宣布通过；
4. 同一模型不同上下文只算「弱独立」；关键评审换模型或加人工抽查。

## 6. 阶段出口条件

| 阶段 | 出口条件 | 证据 | 谁签字 |
|---|---|---|---|
| 设计初稿 | 六维度各有结论；八类确认项已问或已记未决；事实基线齐备 | 维度结论表 + 未决台账 | 作者自检 + 用户确认 |
| 设计评审 | 人判断项逐条有结论；决策表含备选与代价；图文一致 | 评审问题表 + 图审记录 | 独立评审 |
| 实施完成 | 锚点全量核验；数量复算；生成物重建 diff 干净 | 脚本输出 + 复算命令 | 终审 |
| 交付前 | 用户可复现的验证命令与预期输出；未完结清单归属明确；裁定回写齐全 | 复验对比表 + 未完结清单 | 终审 + 用户过目 |

## 7. 交付前必须给用户看的四样证据

1. **结构清单**：完整目录 + 图索引 + 每张图能直接打开看到（不是只给链接）。
2. **逐维结论表**：六维度每个「合格/有条件合格/不合格」+ 一句证据。
3. **未完结清单**：归属阶段、影响、当前替代方案；不得混入「已完成」。
4. **裁定回写状态表**：用户每条裁定 → 落在哪 → 是否生效；作废项附恢复方式。

最后一条：无法亲自验证的（例如终端里渲染不出网页/图），必须明说「我无法验证视觉，请你在浏览器确认，若有问题告诉我具体哪张图哪个位置」——比声称已修好更可信。

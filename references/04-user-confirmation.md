# 04 · 必须与用户确认的事项

## 1. 判断标准

只问一句：**这件事改变的是「做什么」，还是「怎么做」？**
- 「怎么做」= 工程判断，自己定，写进决策表并给推翻条件。
- 「做什么、为谁做、按什么算成功」= 必须用户拍板。

## 2. 八类必须确认的事项

| 类别 | 为什么必须问 | 什么时候问 | 问法（选项 + 代价 + 可逆性） |
|---|---|---|---|
| 业务定位与客户 | 决定验收场景与能力范围，工程推不出来 | 设计第一轮、动笔前 | 「客户是谁 / 平台扮演什么角色」两种理解各导出什么功能与验收场景，请指定一种 |
| 验收通道与验收定义 | 决定端到端在哪跑、什么算通过 | 初稿后、开发前 | 通道 A/B 的验证成本与可信度；默认建议 + 不同意需补什么 |
| 部署形态 | 决定物理架构图、部署清单、验证脚本 | 架构初稿评审时 | 唯一形态 + 明确不做清单；改判代价与需作废的东西 |
| 计费与支付 | 决定是否引入支付、对账、账本边界 | 需求评审时 | 「只计费不支付 / 全支付」的账本与运维代价；可逆性 |
| 技术选型与版本 | 决定依赖、构建链、锁版本 | 选型阶段、升级前 | 候选版本 + 差异 + 锁哪个；谁负责验证兼容 |
| 文档形态（文本/网页/图） | 决定交付物与阅读方式 | 文档开工前 | 载体分工（可视版 / 可 diff 版）+ 生成方式；明确不做什么 |
| 范围与分期 | 决定哪些进本期、哪些外推 | 每期启动前 | 本期/下期/不做 三档，各档的验收影响 |
| 术语与命名 | 决定全仓统一叫法，改名成本很高 | 设计初稿、任何改名提议时 | 候选名 + 影响面（哪些文档、接口、图）；默认沿用哪个 |

补充两类高频外部项：**安全与合规结论**（法务/资质，只能外部给）、**数据口径**（用户数、日活、成本怎么算，业务方给）。

## 3. 问法三条规则

1. **每题自带默认答案**：写成「我的建议是 X；你同意我就按此继续，不同意需要付出 Y」。让用户可以直接说「就按你的」，不必逐题回答。
2. **写清代价与可逆性**：区分「可逆（改一处配置/一行代码）」与「不可逆（环境是物理前提、迁移是大工程）」，不可逆项单独标出。
3. **一次问一组**：集中成一份清单，按「需你点头的范围口径 / 产品取舍 / 外部方 / 我已裁定但你可否决 / 已关闭」分类；用户一次点头可批量落地。

## 4. 待决策清单模板

| # | 问题 | 我的建议（默认按此） | 若同意 | 若不同意 / 代价 | 可逆性 | 落点 |
|---|---|---|---|---|---|---|
| A1 | … | … | 改哪几处 | 需补什么 | 可逆/不可逆 | 文档 §x |

文件头部写清：
- 为什么有这份清单：用户要求「中途不要停」，所以集中问；
- 默认走法：每条给建议，用户不答时按建议继续，但**不把没答当同意**；
- 分类与状态；已关闭的整节保留并写关闭依据（历史台账，原文不删）。

## 5. 用户没回答时

- 记为未决项：编号、问题、建议、代价、可逆性、默认值、默认生效时点、落点。
- 默认值只选**可逆**那一条；不可逆项必须等答复。
- 绝不因为没答就停住，也绝不在文档里假装已定。
- 已经自己裁定的，单列一节「我已裁定、你可一键否决」，写依据与可否决条件——比假装没决定安全。
- 台账长期存在，因此需要「历史台账」标注：哪些路径/服务已退役，按历史读，原文不删。

## 6. 拍板后的回写五件套

1. **裁定原文入档**：用户原话逐字保留，文件头注日期与「这是硬约束」。
2. **升格为项目级硬约束**：写进跨会话记忆（如仓根 `AGENTS.md`），下一轮先读。
3. **受影响处逐处标注**：每个被改判的位置标「某日作废/改判」+ 依据，**原文不删**。
4. **作废清单 + 已改点枚举**：列出作废对象、依据、已改章节位置，便于复核漏没漏。
5. **可恢复性**：分支/目录/配置停用时登记 tip 提交号与恢复命令；不能恢复的写「不可逆」。

## 7. 决策卡模板（问用户时直接套）

```markdown
### 决策 #N：<一句话问题>

- 背景（1–2 句，带证据）：
- 选项：
  - A. <方案>：收益 / 代价 / 可逆性
  - B. <方案>：收益 / 代价 / 可逆性
- 我的建议：A，因为 <理由>。
- 若你同意：我将改 <文档/章节>，影响 <范围>。
- 若你不同意：需要补 <工作>，代价 <时间/风险>。
- 默认：未回复则按 A 继续（仅当 A 可逆）。
```

## 8. 常见误区

| 误区 | 后果 | 正确做法 |
|---|---|---|
| 把「怎么实现」拿去问用户 | 用户嫌烦、给不出有效答案 | 工程判断自己定，给推翻条件即可 |
| 一次只问一个问题，反复打断 | 效率低、用户失去耐心 | 集中成清单，一次点头批量落地 |
| 用户没答就当作同意 | 后面被推翻，整链返工 | 记未决项 + 默认走法 + 可逆性 |
| 只在聊天里说，不写进文档 | 下一轮会话丢失裁定 | 五件套回写 + 项目级硬约束 |
| 改判后把旧内容删掉 | 后人无法判断历史对错，可能改回去 | 原文保留 + 作废标注 |
| 术语/业务定位含糊 | 一次术语错误污染全部文档与图 | 第一轮就定术语表，改名全仓同步 |

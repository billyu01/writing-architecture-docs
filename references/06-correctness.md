# 06 · 一致性正确性规则（架构师红线）

> 这些是「会出事」的架构错误，写文档时一旦出现就判不合格；检查器用启发式拦截，人工评审必须逐条过。

## P0 红线

1. **单事务不得跨聚合**。聚合 = 一致性边界。如果业务要求两个聚合强一致，二选一：
   - 把它们声明为「同一事务边界」（刻意选择，明确写清，不再宣称跨聚合用事件）；
   - 或改补偿式流程：先置中间态（锁定），再推进，失败释放，全程幂等。
   不许一边说「两个聚合」一边「同事务」。
2. **outbox 必须与业务写同事务**（事务内 outbox）。业务提交成功而 outbox 在事务外，崩溃会丢通知且不可重放。写法：业务变更 + outbox 记录同一事务提交，worker 只消费 outbox。
3. **状态迁移与账务写入同事务**。「入账 + 状态→已入账」必须原子；两段事务会留下「账已入、状态未变」。若被迫分两段，必须有补偿任务按账本回填状态。
4. **合并/删除/迁移必须定义关联数据策略**。会员合并要写清：历史积分/券是重绑定还是留原 id、查询如何回退、余额如何迁移、合并是否幂等。

## P1 必补项（缺了不能算「完整」）

- 幂等键规范：谁生成、存哪、唯一索引、TTL、过期清理、键的粒度。
- 错误码完整契约表：每个码的触发条件与返回体。
- 认证细节：令牌校验/内省、会话、过期与刷新。
- 限流规则：阈值、键、降级。
- 网络策略与密钥轮换流程。
- 就绪探针只做核心路径最小检查；外部依赖（如 S3/短信）降级为告警 + 运行时降级，不与就绪硬绑定。
- 容量估算数字：连接数、内存、存储增长、是否分片。
- SLO/SLI：错误预算、错误率目标。
- 数据归档/保留：审计之外的流水、通知、幂等键的清理策略。

## 外部评审常见 P0（逐条自查）

1. 积分/额度账户的归属没定义：账户是按会员、按门店还是按租户？余额唯一索引与流水的维度必须一致，否则同一会员多门店无法表达。
2. 手机号只存 Hash：Hash 不可逆，无法发短信。必须 hash（唯一/检索）+ 加密（业务使用）+ 脱敏（展示）三字段，并写清密钥管理。
3. 幂等混为一谈：业务唯一约束（永久）、请求幂等（TTL）、失败响应缓存（状态机）必须分开定义；账务不能只靠 TTL。
4. 充值对象没定义：充值的是门店额度、会员储值还是预付资金？没定义账户主体就没有余额、消费、退款、冲正语义。
5. 事务只写「一个事务」不够：要写条件更新、版本号、冲突重试次数、超时、热点控制，以及唯一索引兜底。
6. Outbox 只写不消费：必须有状态机、原子领取、租约、重试上限、失败队列；否则多 worker 重复发送。
7. 会员合并只改主表：写别名映射与余额合并规则，历史数据不迁移。
8. 导入没定义重复范围、部分成功、断点续跑与批次大小，10 万行指标没有容量依据。
9. 券状态机缺锁定释放、已核销冲正、过期与核销并发规则。
10. 权限只有认证没有授权矩阵；门店范围不能信任客户端传参。
11. 索引清单与数据生命周期（在线/归档/清理/对账）缺失。
12. 容量模型缺失：门店数、会员数、流水增长、峰值 QPS、Mongo 写入量。

## 常见错误对照

| 症状 | 根因 | 修法 |
|---|---|---|
| 一个事务写两个聚合 | 把一致性边界当成了模块边界 | 合并边界或改补偿流程 |
| outbox 写在事务外 | 没理解事务内 outbox | outbox 与业务同事务 |
| 入账与状态分两段 | 状态机和账务没对齐 | 同事务或补偿回填 |
| 合并只改主表 | 关联数据策略缺失 | 定义重绑定或留原 id 的语义 |
| 就绪探针查所有依赖 | 把降级当成了硬门 | 就绪最小化，依赖降级 |
